# GUÍA COMPLETA PARA LLEVAR BIOFINCAS MONITOR A PRODUCCIÓN

Fecha: 29 de Noviembre de 2025
Versión: 1.0

================================================================================
RESUMEN EJECUTIVO
================================================================================

BioFincas Monitor es una plataforma web de gestión y monitoreo de proyectos 
agrícolas, construida con Next.js 15.1.3, React 19, PostgreSQL y Tailwind CSS. 
Esta guía detalla todas las consideraciones, tiempos estimados y descripción de 
tareas necesarias para llevar la aplicación a un entorno de producción.

Tiempo total estimado para llevar a producción: 40-50 horas

================================================================================
1. VERIFICACIÓN DE PREREQUISITOS (3-4 horas)
================================================================================

1.1 ANÁLISIS DE DEPENDENCIAS Y SEGURIDAD
   - Tiempo: 2 horas
   - Descripción:
     * Auditar todas las dependencias con `npm audit`
     * Verificar vulnerabilidades conocidas (CVEs) en paquetes npm
     * Actualizar paquetes a versiones estables y compatibles
     * Revisar la compatibilidad entre dependencias principales:
       - Next.js 15.1.3 con React 19
       - PostgreSQL client (pg) versión 8.16.3
       - Tailwind CSS 3.4.18
       - D3, Recharts para visualizaciones
     * Evaluar dependencias opcionales y remover si no se usan
   - Archivos clave:
     * package.json
     * package-lock.json
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Ejecutar auditoría de dependencias:
        ```bash
        npm audit
        npm audit --json > audit-report.json
        ```
     
     2. Revisar vulnerabilidades críticas:
        - Abrir audit-report.json
        - Buscar "severity": "critical" o "high"
        - Documentar CVEs encontradas
     
     3. Actualizar paquetes vulnerables:
        ```bash
        npm update [package-name]@[version]
        npm audit fix  # Intento automático
        npm audit fix --force  # Fuerza actualización (cuidado)
        ```
     
     4. Validar compatibilidad:
        ```bash
        npm run build  # Verificar que aún compila
        npm test      # Ejecutar tests
        ```
     
     5. Eliminar dependencias innecesarias:
        ```bash
        npm ls  # Listar todos los paquetes
        npm prune  # Remover dependencias no usadas
        ```
     
     6. Generar reporte final:
        ```bash
        npm audit --audit-level=moderate > final-audit.txt
        ```
        Documentar en un archivo SECURITY_AUDIT.md

1.2 VALIDACIÓN DEL CÓDIGO FUENTE
   - Tiempo: 1-2 horas
   - Descripción:
     * Ejecutar linter con `npm run lint` para verificar código TypeScript
     * Revisar errores de tipo en tsconfig.json
     * Validar que no haya warnings o errores de compilación
     * Revisar código obsoleto o comentarios de desarrollo
     * Verificar que no haya variables de depuración o logs innecesarios
   - Archivos clave:
     * tsconfig.json
     * next.config.ts
     * .eslintrc.json (si existe)
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Ejecutar linter:
        ```bash
        npm run lint
        npm run lint -- --fix  # Arreglar automáticamente
        ```
     
     2. Verificar compilación de TypeScript:
        ```bash
        npx tsc --noEmit  # Verificar tipos sin generar JS
        ```
     
     3. Buscar código de desarrollo:
        ```bash
        grep -r "console\.log" src/ --include="*.ts" --include="*.tsx"
        grep -r "TODO\|FIXME\|HACK" src/ --include="*.ts" --include="*.tsx"
        grep -r "debugger" src/ --include="*.ts" --include="*.tsx"
        ```
     
     4. Remover logs de desarrollo en archivos encontrados
     
     5. Compilar proyecto:
        ```bash
        npm run build
        ```

1.3 VERIFICACIÓN DE CONFIGURACIÓN
   - Tiempo: 1 hora
   - Descripción:
     * Validar que la configuración de Next.js sea óptima
     * Revisar Image Optimization settings
     * Verificar que los path aliases (@/*) funcionen correctamente
     * Validar configuración de Turbopack para compilación rápida
     * Revisar headers de seguridad (CORS, CSP, etc.)
   - Archivos clave:
     * next.config.ts
     * middleware.ts (si existe)
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Actualizar next.config.ts con optimizaciones:
        ```typescript
        const nextConfig: NextConfig = {
          images: { formats: ['image/avif', 'image/webp'], unoptimized: false },
          compress: true,
          productionBrowserSourceMaps: false,
          swcMinify: true,
          headers: async () => [{
            source: '/:path*',
            headers: [
              { key: 'X-Content-Type-Options', value: 'nosniff' },
              { key: 'X-Frame-Options', value: 'DENY' },
              { key: 'X-XSS-Protection', value: '1; mode=block' },
            ],
          }],
        };
        ```
     
     2. Validar path aliases en tsconfig.json funcionan:
        ```bash
        npm run build
        ```
     
     3. Revisar middleware.ts para que esté protegiendo rutas
     
     4. Validar configuración de Tailwind en tailwind.config.ts

2. GESTIÓN DE VARIABLES DE ENTORNO (4-5 horas)
================================================================================

2.1 DEFINICIÓN Y DOCUMENTACIÓN DE VARIABLES
   - Tiempo: 2 horas
   - Descripción:
     * Documentar todas las variables de entorno necesarias:
       - DATABASE_URL: Conexión a PostgreSQL (Prisma Accelerate en prod)
       - POSTGRES_URL: Conexión directa para fallback
       - NEXT_PUBLIC_API_URL: URL de la API en producción
       - SESSION_SECRET: Clave para encriptación de sesiones
       - JWT_SECRET: Clave para tokens JWT (si aplica)
     * Crear archivo .env.production con valores seguros
     * Generar .env.example con placeholders seguros
     * Documentar en README cómo configurar cada variable
   - Archivos a crear/modificar:
     * .env.production
     * .env.example (actualizar)
     * README.md (sección de configuración)
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Actualizar .env.example:
        ```
        # Database
        DATABASE_URL="postgresql://user:password@host:5432/database"
        POSTGRES_URL="postgresql://user:password@host:5432/database"
        
        # API Configuration
        NEXT_PUBLIC_API_URL="https://api.yourdomain.com"
        
        # Security
        SESSION_SECRET="your-secret-key-min-32-chars-long"
        JWT_SECRET="your-jwt-secret-key-min-32-chars-long"
        
        # Node Environment
        NODE_ENV="production"
        ```
     
     2. Generar secretos seguros:
        ```bash
        node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
        ```
        Usar output para SESSION_SECRET y JWT_SECRET
     
     3. Crear .env.production con valores reales (NO comitear)
     
     4. Documentar en README.md sección "Environment Configuration"
     
     5. Crear ENVIRONMENT_VARIABLES.md con explicación de cada variable

2.2 SEGURIDAD DE SECRETS Y CREDENCIALES
   - Tiempo: 1-2 horas
   - Descripción:
     * NUNCA comitear .env con credenciales reales
     * Implementar rotación periódica de secretos (cada 3 meses)
     * Usar gestores de secretos como:
       - Vercel Secrets (si se despliega en Vercel)
       - AWS Secrets Manager (si está en AWS)
       - HashiCorp Vault (si es infraestructura corporativa)
     * Documentar procedimiento de rotación de credenciales
     * Crear plan de recuperación si se compromete un secret
   - Consideraciones de seguridad:
     * Los secrets deben tener permisos mínimos necesarios
     * Usar conexiones SSL para bases de datos
     * Implementar auditoría de acceso a secretos
     * Crear alertas si se accede a secrets de forma anómala
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Agregar .env al .gitignore (si no está):
        ```bash
        echo ".env.local" >> .gitignore
        echo ".env.production" >> .gitignore
        ```
     
     2. Para Vercel: Configurar secrets en dashboard:
        - Ir a Project Settings → Environment Variables
        - Agregar cada variable con su valor
        - Seleccionar ambientes (Development, Preview, Production)
     
     3. Para AWS: Usar AWS Secrets Manager:
        ```bash
        aws secretsmanager create-secret \
          --name biofincas/prod/database \
          --secret-string '{"url":"..."}'
        ```
     
     4. Crear procedimiento de rotación:
        - Crear documento: SECRET_ROTATION_PROCEDURE.md
        - Definir frecuencia: cada 90 días
        - Documentar pasos: generar nuevo secret, actualizar, validar
     
     5. Configurar alertas en el platform (Vercel/AWS)
        para acceso a secretos

2.3 CONFIGURACIÓN DE BASE DE DATOS EN PRODUCCIÓN
   - Tiempo: 1-2 horas
   - Descripción:
     * Migrar base de datos a servidor de producción:
       - Opción A: PostgreSQL en Render, Railway, o similar
       - Opción B: AWS RDS para mayor disponibilidad
       - Opción C: Google Cloud SQL
     * Configurar backups automáticos (diarios)
     * Implementar plan de recuperación ante desastres (DR)
     * Configurar réplicas de lectura para escalabilidad
     * Validar que la base de datos tenga los esquemas necesarios:
       - roles, users, user_sessions, audit_logs
       - products, tasks, phases
       - indicators, outputs, work_packages
     * Ejecutar migraciones de datos si hay esquema anterior
   - Archivos a revisar:
     * src/lib/db.ts (configuración de conexión)
     * src/app/api/setup-rbac/route.ts (schema RBAC)
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Crear base de datos en plataforma elegida (ej: Render):
        ```bash
        # Render proporciona DATABASE_URL y POSTGRES_URL
        # Copiar y guardar en gestor de secretos
        ```
     
     2. Probar conexión:
        ```bash
        npm install pg
        node -e "
          const Pool = require('pg').Pool;
          const pool = new Pool({ connectionString: process.env.DATABASE_URL });
          pool.query('SELECT NOW()', (err, res) => {
            if (err) console.error(err);
            else console.log('Connection successful:', res.rows[0]);
            process.exit();
          });
        "
        ```
     
     3. Ejecutar setup de RBAC:
        ```bash
        curl -X POST https://yourdomain.com/api/setup-rbac
        # O ejecutar localmente contra prod DB
        ```
     
     4. Configurar backups automáticos en el platform
     
     5. Crear índices en base de datos:
        ```sql
        CREATE INDEX idx_product_id ON tasks(product_id);
        CREATE INDEX idx_task_id ON tasks(id);
        CREATE INDEX idx_user_id ON users(id);
        CREATE INDEX idx_status_id ON tasks(status_id);
        CREATE INDEX idx_created_at ON tasks(created_at);
        ```
     
     6. Validar estructura de tablas:
        ```bash
        curl -X GET https://yourdomain.com/api/table-structure
        ```

3. OPTIMIZACIÓN DE PERFORMANCE (6-8 horas)
================================================================================

3.1 OPTIMIZACIÓN DE BUNDLE Y CÓDIGO
   - Tiempo: 2-3 horas
   - Descripción:
     * Analizar tamaño del bundle con `npm run build`
     * Implementar code splitting automático de Next.js
     * Lazy loading de componentes pesados (Gantt, gráficos, modales)
     * Optimizar imports - evitar importar librerías completas
     * Revisar y remover dead code
     * Implementar dynamic imports para rutas no críticas
     * Validar que los assets estáticos no excedan 50MB
   - Herramientas recomendadas:
     * next/bundle-analyzer
     * webpack-bundle-analyzer
   - Objetivos:
     * Bundle de JavaScript < 500KB (comprimido)
     * First Contentful Paint < 1.5s
     * Lighthouse score > 80
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Instalar bundle analyzer:
        ```bash
        npm install --save-dev @next/bundle-analyzer
        ```
     
     2. Actualizar next.config.ts:
        ```typescript
        const withBundleAnalyzer = require('@next/bundle-analyzer')({
          enabled: process.env.ANALYZE === 'true',
        });
        module.exports = withBundleAnalyzer(nextConfig);
        ```
     
     3. Analizar bundle:
        ```bash
        ANALYZE=true npm run build
        ```
        Esto genera archivos .html para visualizar
     
     4. Implementar dynamic imports para componentes pesados:
        ```typescript
        import dynamic from 'next/dynamic';
        const GanttChart = dynamic(() => import('@/components/gantt-chart'), {
          loading: () => <p>Cargando...</p>,
          ssr: false,
        });
        ```
     
     5. Remover imports no usados (dead code):
        ```bash
        grep -r "import" src/ | grep -v "from" | grep -v "="
        ```
     
     6. Verificar tamaño final:
        ```bash
        npm run build
        # Revisar .next/static/chunks
        ```
        Objetivo: main bundle < 500KB

3.2 OPTIMIZACIÓN DE IMÁGENES Y ASSETS
   - Tiempo: 1-2 horas
   - Descripción:
     * Usar componente <Image> de Next.js para todas las imágenes
     * Implementar lazy loading de imágenes
     * Optimizar formatos: WebP para navegadores modernos
     * Configurar srcset para responsive images
     * Comprimir imágenes antes de deployar
     * Usar CDN para servir assets estáticos
     * Validar que las imágenes tengan dimensiones correctas
   - Consideraciones:
     * Máximo 200KB por imagen
     * Usar AVIF o WebP cuando sea posible
     * Implementar blur placeholder para UX
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Usar componente Image de Next.js:
        ```typescript
        import Image from 'next/image';
        
        <Image
          src="/products/sample.jpg"
          alt="Product"
          width={400}
          height={300}
          placeholder="blur"
          blurDataURL="data:image/..."
          priority={false}
        />
        ```
     
     2. Comprimir imágenes antes de subir:
        ```bash
        # Instalar imagemin
        npm install --save-dev imagemin imagemin-mozjpeg imagemin-pngquant
        
        # Script de compresión (en package.json):
        "compress-images": "imagemin public/**/*.{jpg,png} --out-dir=public"
        ```
     
     3. Configurar próxima generación de formatos en next.config.ts:
        ```typescript
        images: {
          formats: ['image/avif', 'image/webp'],
          unoptimized: false,
        }
        ```
     
     4. Validar tamaño de imágenes:
        ```bash
        find public -type f \( -name "*.jpg" -o -name "*.png" -o -name "*.webp" \) \
          -exec ls -lh {} \; | awk '{print $5, $9}'
        ```

3.3 OPTIMIZACIÓN DE BASE DE DATOS
   - Tiempo: 2-3 horas
   - Descripción:
     * Crear índices en columnas frecuentemente consultadas:
       - product_id, task_id, status_id, user_id
       - created_at, updated_at para filtros por fecha
     * Implementar paginación en listados (máximo 50 registros por página)
     * Usar prepared statements para prevenir SQL injection
     * Implementar caché en memoria para datos que no cambian frecuentemente:
       - Roles y permisos (5 minutos)
       - Países y organizaciones (1 hora)
       - Usuarios (30 minutos)
     * Validar que las queries no hagan N+1
     * Implementar connection pooling en PostgreSQL
   - Configuración recomendada:
     * Pool size: 20-30 conexiones
     * Connection timeout: 5000ms
     * Idle timeout: 30000ms
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Crear índices en PostgreSQL:
        ```sql
        CREATE INDEX idx_product_id ON tasks(product_id);
        CREATE INDEX idx_task_id ON tasks(id);
        CREATE INDEX idx_status_id ON tasks(status_id);
        CREATE INDEX idx_user_id ON users(id);
        CREATE INDEX idx_created_at ON tasks(created_at);
        CREATE INDEX idx_updated_at ON tasks(updated_at);
        
        -- Índices compuestos para queries frecuentes
        CREATE INDEX idx_product_status ON tasks(product_id, status_id);
        ```
     
     2. Implementar paginación en API:
        ```typescript
        // src/app/api/products/route.ts
        const limit = 50;
        const offset = (page - 1) * limit;
        const result = await db.query(
          'SELECT * FROM products LIMIT $1 OFFSET $2',
          [limit, offset]
        );
        ```
     
     3. Configurar connection pooling en src/lib/db.ts:
        ```typescript
        const pool = new Pool({
          connectionString: process.env.DATABASE_URL,
          max: 20,
          idleTimeoutMillis: 30000,
          connectionTimeoutMillis: 5000,
        });
        ```
     
     4. Implementar caché con Redis (opcional):
        ```bash
        npm install redis
        ```
        Crear src/lib/cache.ts con wrapper de Redis

3.4 OPTIMIZACIÓN DE RED Y CDN
   - Tiempo: 1-2 horas
   - Descripción:
     * Implementar compresión gzip en responses (Next.js por defecto)
     * Activar compression Brotli para mejor ratio
     * Implementar HTTP/2 o HTTP/3
     * Usar CDN para assets estáticos (Vercel CDN, Cloudflare, AWS CloudFront)
     * Configurar cache headers apropiados:
       - Assets estáticos: 1 año (cache agresivo)
       - HTML: no-cache, must-revalidate
       - API responses: según su naturaleza
     * Implementar HSTS (HTTP Strict Transport Security)
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Configurar headers de caché en next.config.ts:
        ```typescript
        headers: async () => [
          {
            source: '/api/:path*',
            headers: [
              { key: 'Cache-Control', value: 'public, s-maxage=60' },
            ],
          },
          {
            source: '/_next/static/:path*',
            headers: [
              { key: 'Cache-Control', value: 'public, max-age=31536000, immutable' },
            ],
          },
        ],
        ```
     
     2. Implementar Brotli compression:
        - En Vercel: automático
        - En AWS CloudFront: habilitar en distribution
        - En self-hosted: configurar nginx/apache
     
     3. Configurar HSTS:
        ```typescript
        headers: async () => [{
          source: '/:path*',
          headers: [{
            key: 'Strict-Transport-Security',
            value: 'max-age=63072000; includeSubDomains; preload'
          }],
        }],
        ```
     
     4. Si usa Vercel: CDN automático
        Si usa CloudFront:
        ```bash
        # Configurar en AWS CloudFront distribution
        # Enable compression: Yes
        # Viewer protocol policy: Redirect HTTP to HTTPS
        ```
     
     5. Validar compresión:
        ```bash
        curl -I -H "Accept-Encoding: gzip" https://yourdomain.com
        # Verificar que Content-Encoding: gzip está en respuesta
        ```

4. SEGURIDAD (10-12 horas)
================================================================================

4.1 AUTENTICACIÓN Y AUTORIZACIÓN
   - Tiempo: 2-3 horas
   - Descripción:
     * Validar que bcrypt está siendo usado para hashing de contraseñas
     * Implementar política de contraseñas fuerte:
       - Mínimo 12 caracteres
       - Combinación de mayúsculas, minúsculas, números y símbolos
       - No permitir contraseñas comunes
     * Implementar rate limiting en login:
       - Máximo 5 intentos fallidos por IP en 15 minutos
       - Bloquear temporalmente después de ciertos intentos
     * Configurar sesiones seguras:
       - HTTP only cookies
       - Secure flag (solo HTTPS)
       - SameSite = Strict
       - Expiración: 7 días máximo
     * Implementar 2FA (Two-Factor Authentication) opcional
     * Validar que el RBAC está correctamente configurado:
       - admin, manager, user, viewer
       - Permisos granulares por recurso
   - Archivos a revisar:
     * src/app/api/auth/login/route.ts
     * src/middleware.ts
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Verificar bcrypt en login route:
        ```typescript
        // src/app/api/auth/login/route.ts
        import bcrypt from 'bcryptjs';
        
        const isValidPassword = await bcrypt.compare(
          providedPassword,
          storedHash
        );
        ```
     
     2. Validar política de contraseñas:
        ```typescript
        // Crear src/lib/password-validation.ts
        const validatePassword = (password: string): string[] => {
          const errors = [];
          if (password.length < 12) errors.push('Min 12 chars');
          if (!/[A-Z]/.test(password)) errors.push('Uppercase required');
          if (!/[a-z]/.test(password)) errors.push('Lowercase required');
          if (!/[0-9]/.test(password)) errors.push('Number required');
          if (!/[!@#$%^&*]/.test(password)) errors.push('Symbol required');
          return errors;
        };
        ```
     
     3. Implementar rate limiting:
        ```bash
        npm install express-rate-limit
        ```
        En src/app/api/auth/login/route.ts:
        ```typescript
        import rateLimit from 'express-rate-limit';
        const limiter = rateLimit({
          windowMs: 15 * 60 * 1000,
          max: 5,
          message: 'Too many login attempts',
        });
        ```
     
     4. Configurar sesiones seguras:
        ```typescript
        // En middleware.ts o route handler
        response.cookies.set('session', token, {
          httpOnly: true,
          secure: process.env.NODE_ENV === 'production',
          sameSite: 'strict',
          maxAge: 7 * 24 * 60 * 60, // 7 días
        });
        ```
     
     5. Validar RBAC:
        ```bash
        curl -X GET https://yourdomain.com/api/users \
          -H "Authorization: Bearer $TOKEN"
        # Debe retornar 403 si usuario no tiene permiso
        ```

4.2 PROTECCIÓN CONTRA VULNERABILIDADES WEB
   - Tiempo: 2-3 horas
   - Descripción:
     * Implementar CSRF tokens en formularios
     * Validar y sanitizar todas las entradas del usuario
     * Implementar rate limiting global:
       - Máximo 1000 requests por IP por minuto
       - Por endpoint específico según criticidad
     * Prevenir XSS:
       - Usar Content-Type: application/json en APIs
       - Validar y escapar contenido renderizado
       - Implementar CSP (Content Security Policy)
     * Prevenir SQL Injection:
       - Usar prepared statements (ya implementado con pg)
       - Validar tipos de datos en inputs
     * Validar tamaño de payloads:
       - Máximo 10MB por request
       - Máximo 1MB por field
   - Headers de seguridad a agregar:
     * X-Content-Type-Options: nosniff
     * X-Frame-Options: DENY
     * X-XSS-Protection: 1; mode=block
     * Referrer-Policy: strict-origin-when-cross-origin
     * Permissions-Policy: camera=(), microphone=(), geolocation=()
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Implementar CSP headers en next.config.ts:
        ```typescript
        // next.config.ts
        const securityHeaders = [
          {
            key: 'Content-Security-Policy',
            value: "default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' data:;"
          },
          {
            key: 'X-Content-Type-Options',
            value: 'nosniff'
          },
          {
            key: 'X-Frame-Options',
            value: 'DENY'
          },
          {
            key: 'X-XSS-Protection',
            value: '1; mode=block'
          },
          {
            key: 'Referrer-Policy',
            value: 'strict-origin-when-cross-origin'
          },
          {
            key: 'Permissions-Policy',
            value: 'camera=(), microphone=(), geolocation=()'
          }
        ];
        
        module.exports = {
          async headers() {
            return [
              {
                source: '/:path*',
                headers: securityHeaders,
              }
            ];
          }
        };
        ```
     
     2. Implementar rate limiting:
        ```bash
        npm install express-rate-limit
        ```
        Crear src/lib/rate-limit.ts:
        ```typescript
        import rateLimit from 'express-rate-limit';
        
        export const loginLimiter = rateLimit({
          windowMs: 15 * 60 * 1000, // 15 minutos
          max: 5, // 5 intentos
          message: 'Too many login attempts',
          standardHeaders: true,
          legacyHeaders: false,
        });
        
        export const globalLimiter = rateLimit({
          windowMs: 1 * 60 * 1000, // 1 minuto
          max: 1000, // 1000 requests
          skip: (req) => req.method === 'GET',
        });
        ```
     
     3. Aplicar CSRF protection:
        ```bash
        npm install csrf-csrf
        ```

6.4 RESPALDO Y RECUPERACIÓN
   - Tiempo: 1-1.5 horas
   - Descripción:
     * Implementar backup automático de base de datos:
       - Frecuencia: Diariamente a las 2 AM
       - Retención: 30 días locales, 1 año en archive
       - Stored offsite (AWS S3, Google Cloud Storage, etc.)
     * Implementar backup de archivos estáticos:
       - Documentos subidos por usuarios
       - Imágenes
       - Reportes
     * Probar restore mensualmente:
       - Restaurar base de datos
       - Validar integridad de datos
       - Documentar tiempo de recovery
     * RTO (Recovery Time Objective): < 1 hora
     * RPO (Recovery Point Objective): < 1 día
   - Herramientas recomendadas:
     * AWS Backup, Backblaze, Veeam
     * Automatizar con scripts shell o Lambda
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Crear script de backup manual:
        ```bash
        # Crear backup-db.sh
        #!/bin/bash
        
        DB_NAME=product_report
        DB_USER=postgres
        BACKUP_DIR=/backups
        DATE=$(date +%Y%m%d_%H%M%S)
        
        mkdir -p $BACKUP_DIR
        
        pg_dump -U $DB_USER -d $DB_NAME | gzip > $BACKUP_DIR/backup_$DATE.sql.gz
        
        # Archivar backups antiguos (> 30 días) a S3
        aws s3 cp $BACKUP_DIR/backup_*.sql.gz s3://my-bucket/db-backups/ \
          --sse AES256
        
        find $BACKUP_DIR -name "backup_*.sql.gz" -mtime +30 -delete
        ```
        ```bash
        chmod +x backup-db.sh
        # Agregar a crontab
        crontab -e
        # 0 2 * * * /path/to/backup-db.sh
        ```
     
     2. Restaurar backup:
        ```bash
        #!/bin/bash
        # restore-db.sh
        
        BACKUP_FILE=$1
        DB_NAME=product_report
        DB_USER=postgres
        
        # Crear DB vacía
        dropdb -U $DB_USER $DB_NAME
        createdb -U $DB_USER $DB_NAME
        
        # Restaurar
        gunzip -c $BACKUP_FILE | psql -U $DB_USER -d $DB_NAME
        
        echo "Database restored from $BACKUP_FILE"
        ```
        ```bash
        ./restore-db.sh /backups/backup_20240115_020000.sql.gz
        ```
     
     3. Backup de archivos:
        ```bash
        #!/bin/bash
        # backup-files.sh
        
        BACKUP_DATE=$(date +%Y%m%d_%H%M%S)
        
        # Si usa S3 para uploads
        aws s3 sync s3://my-uploads s3://my-backups/files-$BACKUP_DATE/
        
        # Si usa filesystem local
        tar -czf /backups/files-$BACKUP_DATE.tar.gz /var/www/uploads/
        aws s3 cp /backups/files-$BACKUP_DATE.tar.gz s3://my-backups/
        ```
     
     4. Prueba de restore mensual:
        ```bash

        ```
        Crear src/lib/cloud-logger.ts:

        ```typescript
        import winston from 'winston';
        import CloudWatchTransport from 'winston-cloudwatch';
        
        export const cloudLogger = winston.createLogger({
          transports: [
            new CloudWatchTransport({
              logGroupName: '/product-report/app',
              logStreamName: `${process.env.NODE_ENV}`,
              awsAccessKeyId: process.env.AWS_ACCESS_KEY_ID,
              awsSecretKey: process.env.AWS_SECRET_ACCESS_KEY,
              awsRegion: process.env.AWS_REGION,

                return `[${level}] ${message} ${JSON.stringify(meta)}`;
              },
            }),
          ],
        });
        ```

8.1 MONITOREO DURANTE PRIMERAS 24 HORAS
   - Tiempo: 2-3 horas (distribuidas a lo largo del día)
   - Descripción:
     * Monitoreo cercano de:
       - Errores en logs
       - Performance (latencia, response times)
       - Comportamiento de usuarios
       - Reporte de issues
     * Estar disponible para soporte inmediato
     * Tener rollback plan listo en caso de critical issues
     * Comunicar status a stakeholders cada 4 horas
   
   - HOW TO - IMPLEMENTACIÓN:
     1. Crear script de monitoreo:
        ```bash
        #!/bin/bash
        # monitor-24h.sh
        
        DOMAIN="https://yourdomain.com"
        INTERVAL=60 # segundos
        LOG_FILE="monitoring-$(date +%Y%m%d_%H%M%S).log"
        
        while true; do
          TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
          
          # Health check
          HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" $DOMAIN/api/health)
          RESPONSE_TIME=$(curl -s -o /dev/null -w "%{time_total}" $DOMAIN/api/health)
          
          # Error rate (último 5 minutos)
          ERROR_COUNT=$(grep ERROR /var/log/app/error.log | wc -l)
          
          echo "[$TIMESTAMP] Status: $HTTP_CODE | Response: ${RESPONSE_TIME}s | Errors: $ERROR_COUNT" >> $LOG_FILE
          
          # Alert si hay problemas
          if [ "$HTTP_CODE" != "200" ]; then
            echo "⚠️  ALERT: Health check failed with code $HTTP_CODE" | \
              mail -s "ALERT: Health check failed" support@oroverde.com
          fi
          
          if (( $(echo "$RESPONSE_TIME > 1.0" | bc -l) )); then
            echo "⚠️  ALERT: Response time too high: ${RESPONSE_TIME}s"
          fi
          
          sleep $INTERVAL
        done
        ```
     
     2. Revisar logs continuamente:
        ```bash

        tail -f /var/log/app/error.log | grep ERROR
        
        # Terminal 2: Monitorear acceso
        ```
